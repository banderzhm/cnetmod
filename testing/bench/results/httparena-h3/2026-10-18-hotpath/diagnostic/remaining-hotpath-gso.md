## ACK and packing costs are separate

Only ack-eliciting received packets enter the bounded PN set (`quic_connection.cpp:2343–2357`, helper177–185). Pure ACK traffic does not create an ACK-of-ACK loop. ACK encoding builds range metadata (`140–174`); the packer adds it before STREAM and clears pending state only after authenticated packet construction (`4207–4215,4428–4432`).

A full-budget queued STREAM plus a pending ACK can produce a small ACK-only packet because the STREAM no longer fits the remainder. Tail frames can share a packet with other small frames, but the scheduler does not skip a nonfitting high-priority head to bin-pack lower-priority streams. Quantify ACK-only packets, residual bytes, requeues and frame classes before changing fairness or ACK timing. Current client-sent UDP/response0.43 combines requests/ACK/control; it is not one ACK per server packet.

Late STREAM splitting is a separate, less minimal change: quic_send_frame equality (`quic_send_pipeline.cpp:164–178`) compares full header/body slice identity, and recovery uses it to resolve delivered PTO aliases (`quic_recovery.cpp:181–192`). Splitting an already transmitted/retransmitted frame changes that identity. Restricting a split to never-sent frames requires reliable provenance; coming from the scheduler is insufficient because it also requeues retransmissions (`quic_send_pipeline.cpp:285–297`). FIN, offsets, priority restoration, original/probe ACK aliasing and shared-owner release all need coverage. This is not a safe shortcut for the failed large-MTU experiment.

## Minimal explicit GSO architecture, preserving1472 and each QUIC packet

Linux UDP_SEGMENT can send a combined buffer that the kernel segments later; each resulting datagram must still satisfy normal MTU rules. It supports per-message ancillary data and depends on checksum offload. The documented API limit is64 segments, so the current16-packet bound is comfortably smaller. [Linux udp(7)](https://man7.org/linux/man-pages/man7/udp.7.html). sendmmsg reports an accepted message prefix and can lose the subsequent error after a positive return. [Linux sendmmsg(2)](https://man7.org/linux/man-pages/man2/sendmmsg.2.html). These APIs describe UDP submission, not QUIC packet coalescing or larger wire MTU.

Use an explicit QUIC-owned, opt-in segmented-batch entry beside the existing adapter; leave the generic async_sendto_batch contract unchanged. The current udp_send_datagram (`async_op.cppm:371–375`) has only bytes+peer and cannot express segmentation metadata or a group-to-original-count map. Keep framing in QUIC and platform control-message construction in the executor backend, with declarations/implementation split as usual. No new types-named file or extra responsibilities in the large connection class are needed.

1. Input remains the original ordered sequence of independently sealed datagrams. Group only adjacent packets sharing socket, destination, path and all ancillary semantics. Each interior packet must have exactly the stride length; the last may be shorter. A short packet in the middle ends a group. Different lengths can simply remain ordinary messages. Do not append bytes outside authenticated QUIC ciphertext to force equal lengths. Padding, if ever chosen, must happen before encryption and be included in congestion/pacing accounting; it is outside the minimal candidate.
2. In a synchronous Linux helper, one grouped mmsghdr can use several existing packet buffers as iovec entries, plus a per-message UDP_SEGMENT stride. The kernel sees their logical concatenation; no extra user-space concatenation slab is necessary. Keep the existing bound of16 original datagrams, so a1472-sized group is at most23,552 bytes. The copied plaintext/ciphertext remains exactly the same as ordinary submission.
3. Initially support only the immediate sendmmsg attempt. Stack iovec/address/cmsg scratch does not escape. On EAGAIN, use the existing original-datagram adapter/writability path; on a recognized zero-progress offload/size rejection, make one ordinary attempt on the exact original datagrams. The minimal prepared candidate has no capability cache: it does not permanently disable GSO based on an ambiguous errno. Do not create a new io_uring grouped-SENDMSG awaiter in the first candidate. That would require frame-owned ancillary/iovec lifetime through original and cancel CQEs. Never fall back by sending the logical combined buffer as one ordinary UDP datagram.
4. A successful GSO group represents all its original datagrams, not one packet of progress. Convert a positive sendmmsg message count through a fixed group-prefix count table. Return accepted original-datagram count to the existing caller. After a positive prefix, retry only the unaccepted suffix; never retry an accepted group. A negative unsupported attempt has no new accepted prefix. The prepared candidate also permits one ordinary retry for ambiguous EINVAL/EIO/EMSGSIZE, preserving the ordinary result as authoritative; it does not swallow persistent native errors or label every network error a capability failure.
5. Preserve per-packet PN, AEAD, header protection, recovery frame owner, bytes-in-flight and cwnd admission. Pacing already charges sum of all packet bytes before submission; preserve that sum, not the GSO message count. Successful progress still wins a concurrent cancellation request. Queue accepted completion remains distinct from transport/peer delivery. Borrowed packet buffers stay owned until the original adapter completion, exactly as now.
6. Require explicit socket-option ownership: existing UDP_CORK, native UDP_SEGMENT defaults, MSG_MORE and external native option mutation cannot be silently overridden. Primary library-controlled sockets are the possible scope; multipath/application-owned sockets and unknown option state use the ordinary path. If the existing exposed native handle prevents this guarantee, the optimization requires explicit opt-in ownership/option constraints rather than changing generic UDP semantics. Non-Linux backends keep the ordinary path.

This changes kernel aggregation; it does not reduce wire UDP/QUIC packet count or per-packet crypto/recovery allocation. GRO can change the peer's observed receive unit, which must not be reported as fewer wire packets. The kernel documentation distinguishes segmentation and receive aggregation. [Segmentation offloads](https://docs.kernel.org/networking/segmentation-offloads.html).

## Why the old65527 result does not settle current PMTU priority

The old external experiment `/var/tmp/cnetmod-h3-large-udp-ab-1792311419` was16:16–16:18 on2026-10-18, before reliable HANDSHAKE_DONE and later lifetime/error fixes. Binary639a91c7... changed only arena discovery/receive ceilings1472→65527, relinking old stage2-before-gso runtime. Its three static rates were80965/83316/83616 completed-header-count per elapsed second versus321627/336461/338286 control; receivedUDP/2xx1.31–1.43 versus12.06. Baseline also fell roughly3.0M→304–311k and serverCPU110→11seconds; staticCPU97→15seconds. Low CPU supports an under-progress/wait hypothesis, not proof of a particular failure. Legacy runner checked failed=0 and2xx, not today's strict done=succeeded=2xx contract. Logs contain no probe target/ACK, syscall errno or stall state. Summary/scripts/link command are archived in `remaining-hotpath-gso-evidence/old-large-pmtu/`; large binary/log directory stays external.

65527 exceeds ordinary IPv4 maximum payload65507; IPv6 has a different header allowance. However the setter is only a ceiling: code starts1200, increases probes by128 (`connection.cpp:783,968–970`), validates ACK before raising (`2954–2967`) and caps by peer/local limits (`909–917`). Thus the old experiment does not prove that a65527 UDP was actually attempted or that the20-byte discrepancy caused its slowdown. Current receive allocation uses configured max payload (`http3_server.cpp:1992–1995`), so1472 configuration would truncate large ingress but raising the ceiling also raises receive capacity; it additionally changes pool/memory cost. The4MiB socket receive budget (`846,902`) is another controlled variable. Unsegmented roughly46460-byte agensio syscall messages are real evidence of large UDP submission, not necessarily proof of its wire fragmentation policy.

There is a confirmed independent PMTU/CC design gap. NewReno/CUBIC initialcwnd14720 and MSS1472 remain fixed (`congestion_control.cppm:44–47,76–81`); minimumcwnd=2944 (`congestion_control.cpp:13,57,181`), ACK-growth MSS remains1472 (`41,154`), as does BBR's size model (`cppm:122–129`). Probe ACK only raises path ceiling; it does not update CC. Writes prebuild whole STREAM frames against the larger PMTU (`connection.cpp:4737–4778`), then packing rejects/requeues the unchanged frame if remainingcwnd is smaller (`4383–4412`). After loss, even zero flight can leave an oversized never-sent frame unable to fit; absent inflight there need not be a PTO to recover it. Probe growth itself can also become blocked once the next padded PING exceeds availablecwnd. This is a concrete reachable design risk, not a proven diagnosis of the historical run.

RFC9002§7.2 recommends recalculating the initial window when MDS changes and a minimum of2*MDS;§7.3.3 limits NewReno avoidance growth per acknowledged window to oneMDS. The fixed model is inconsistent with the new larger validated send size. A correction must preserve congestion admission, update per-path MDS/policy and test loss/min-window behavior; never arbitrarily bypass cwnd. Splitting can be restricted to provably never-sent frames, preserving FIN/offsets/priority/shared owner and existing retransmission identity. Previously sent/probe aliases need range-aware delivery semantics before splitting. [RFC9002](https://www.rfc-editor.org/rfc/rfc9002.html#section-7.2).

Root assigned dynamic-MDS design to a separate review. Keep the explicit GSO candidate independent and default-off while that gap is unresolved. Do not rerun a simple65507 ceiling replacement as an accepted optimization.
