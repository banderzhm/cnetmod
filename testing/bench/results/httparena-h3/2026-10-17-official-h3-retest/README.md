# 官方 HTTP/3 复测与连接回收追踪

用户明确交付测试令牌后，串行完成 27 个计时轮次：`8525da3b` 的完整对照组
21 轮，加上定时器弱引用修复 `ea419cb4` 后的 cnetmod 6 轮。两组分别保存，
不合并选优、不丢弃失败轮次。27 轮结束即停止计时负载并释放令牌。

计时结果仍有问题：最后一组 static-h3 共 134,681 个已完成请求，1 个失败，
0 errored、0 timeout、0 个非 2xx；未再记录 QPACK 解压错误，但这个失败的原因
尚未隔离。内存峰值依然逐轮上升，不能据此声称持续增长已解决。

释放令牌后的低负载诊断进一步复现了空闲超时的路由回收遗漏。该后续修复与回归
属于更新的源码，**不包含在下面 27 轮的被测二进制中**；后续正式复测需要重新
取得共享测试令牌。

## 后续低负载修复与回归

`ea419cb4` 把失效定时器的连接所有权改为弱引用，避免旧条目独自延长连接生命周期。
但定时器超时后仍缺少 `refresh_connection_routes()`：没有后续报文时，已关闭连接
继续留在 CID 路由表和会话表中。后续修复在定时器驱动后执行相同的路由回收。
新增 `statistics().active_connections` 原子快照，按连接而不是 CID 计数，并汇总
多 worker 的数值，便于验证和监测这种滞留。

`http3_idle_cleanup.py` 只建立 4 条连接：保留探测连接，让另外 3 个客户端直接退出，
不发送 QUIC 关闭帧。修复前，超过默认 30 秒空闲期限后，计数仍为 4，持续到
40 秒检查结束，确定性失败；日志保存在 `idle-cleanup-validation/linux-before-fix.log`。
该测试不修改默认超时、不用高负载、不计吞吐量。

定时器弱引用阶段的 Windows Release 构建及 4 项 CTest 全通过；Linux 扩展回归
首次 7/8 通过，动态 QPACK 在默认禁用 push 的检查处出现一次 30 秒断连。
单独复测及随后连续 5 次通过，原因未确认，原始失败日志全部保留在
`timer-fix-validation/`。Windows 普通 E2E 一次用时 31.57 秒但通过，不能将其
和 Linux 的失败混为一谈。没有删除失败输出或把重测当成首次通过。

最新空闲回收修复的 Linux 9 项回归全部通过；空闲用例在约 30.1 秒观察到
活动连接数从 4 回到 1。Windows Release 构建通过，4 项原有回归及新增的
空闲回收用例共 5 项通过；原生空闲回收在约 30.07 秒从 4 回到 1。
Windows 原生 curl/nghttp3 缺项仍保留为 skipped，不计为 peer 通过。
验证日志位于 `idle-cleanup-validation/`。它尚无新的正式压测结果。27 轮短测均不能证明长期内存平台期；最后那 1 个静态失败仍需进一步追踪。
