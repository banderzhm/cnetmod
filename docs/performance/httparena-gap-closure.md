# HttpArena Gap Closure

## Scope

This document is the single execution queue for closing cnetmod's remaining
HttpArena gaps. Only one item may have the `active` state. A new item starts
only after the current item has passed its correctness, performance, and
cross-profile gates or has been rejected with recorded measurements.

The append-only execution record is
[`httparena-gap-closure-log.md`](httparena-gap-closure-log.md). The plan owns
ordering and gates; the log owns commands, measurements, code revisions,
failures, decisions, and handoff state. Do not replace historical log entries
when a conclusion changes. Add a later entry that supersedes the earlier one.

The baseline is the result set generated by HttpArena commit `2802675ec` from
the cnetmod run published on 2026-10-30. Throughput gaps compare the average of
the scored connection rows with the fastest published entry for that profile.
Composite rank and individual profile rank are different measurements; both
must be retained in reports.

## Acceptance contract

Every item uses the same compiler, CPU target, allocator, LTO setting, worker
count, CPU affinity, kernel, load generator, duration, and connection matrix
for its baseline and candidate.

1. Run the official profile for three rounds and retain every round.
2. Record throughput, server CPU per request, memory, mean latency, p99, p99.9,
   reconnects, and every available error counter.
3. Pass the focused protocol tests in Release mode.
4. Run the directly related HttpArena profiles. A median regression above 1%
   rejects the change.
5. Before integration, run HTTP/1.1, HTTP/2 TLS and h2c, HTTP/3, WebSocket,
   gRPC, and Gateway smoke tests.
6. Do not add benchmark detection, hidden environment behavior, reduced
   protocol validation, or benchmark-only framework APIs.

## Ordered execution queue

### G1 - Close the same-edge HTTP/3 Gateway gap

**State:** completed locally - candidate retained

The published cnetmod and vanilla adapters use the same stock Caddy edge, the
same 16/16 physical-core split, HTTP/1.1 loopback forwarding, five-minute
keepalive, and a 2048-connection idle pool. Replacing Caddy would change the
tested stack without first explaining why cnetmod is slower under the same
edge. G1 therefore keeps Caddy and isolates the backend difference.

At 64 connections cnetmod reaches 81,481 requests per second and vanilla
reaches 92,115. The cnetmod backend consumes 343% CPU while vanilla consumes
228%. At 256 connections the gap narrows to 60,476 versus 62,102, while the
cnetmod backend still consumes 251% CPU versus 140%. These measurements point
to backend request cost, connection distribution, or response timing before
they point to the common edge.

Work:

- reproduce cnetmod and vanilla with the unchanged Caddy configuration;
- profile the cnetmod backend separately from Caddy at 64 and 256 connections;
- measure accepted connections per worker, requests per backend connection,
  parser and router CPU, response serialization, send submissions, wakeups,
  and Caddy upstream wait time;
- remove only costs confirmed inside cnetmod's ordinary HTTP/1.1 backend path;
- retain the same response contract, Caddy configuration, and CPU split.

Gate:

- official validation passes;
- three matched cnetmod and vanilla rounds pass at 64 and 256 connections;
- cnetmod backend CPU per completed request decreases and gateway-h3 median
  improves without moving work into Caddy;
- baseline, limited-conn, gateway-64, and production-stack do not regress.

### W1 - Remove ordinary WebSocket receive overhead

**State:** retained locally

Measure one-shot receive submission, multishot activation, buffer recycling,
frame parsing, masking, callback dispatch, and write submission. Compare eager
shared multishot receive with the current adaptive switch. Keep the mode that
improves ordinary echo without reducing limited-connection performance.

### W2 - Remove WebSocket echo copies and excess writes

**State:** retained locally

Keep complete RFC 6455 validation, but let the synchronous message loop encode
the server frame header separately from the borrowed payload. Batch complete
pipeline frames into the minimum safe number of writes without retaining views
after the receive buffer is recycled.

The retained implementation reuses the four mask-key bytes in each validated
client frame as response-header space. A single echo becomes one contiguous
borrowed write. A receive burst uses one scatter/gather submission, with one
buffer per response frame. TLS, cancellation, fragmented messages, control
frames, and modified application output retain their prior owning paths.

### W3 - Shorten WebSocket upgrade and retirement

**State:** retained locally

Profile the ten-message connection lifecycle. Remove avoidable handshake
allocations, parser materialization, close-path submissions, and cross-loop
wakeups. Do not cache request-dependent accept keys.

The retained change removes the second type-erased callback created during
HTTP-to-WebSocket handoff. The server now carries the existing callback and
header snapshot in one internal state object. Public upgrade APIs and the
request-dependent accept key remain unchanged.

### H1 - Finish the HTTP/1 fixed-response path

**State:** completed locally - no additional candidate retained

Measure prepared-response fallbacks, parser work, coroutine frames, io_uring
submissions, and response serialization. Complete the transport-owned small
response path while preserving middleware-visible response semantics.

### H2 - Reduce HTTP/1 connection churn

**State:** completed locally - no additional candidate retained

Apply the H1 profile findings to accept, handshake, request retirement, and
close processing. This item targets `limited-conn` and must retain baseline
throughput.

### H3 - Scale delayed requests without timer churn

**State:** completed locally - no candidate retained

Profile the 32K delayed-request case. Check timer-queue insertion, cancellation,
ready-queue batching, coroutine resumption, and worker balance. The ten
millisecond route delay and cancellation behavior remain unchanged.

### T1 - Consolidate TLS small-response writes

**State:** completed locally - no candidate retained

Measure BIO copies, encryption calls, TLS records, and socket writes for
`json-tls` and `baseline-h2`. Batch HEADERS and small DATA where permitted and
retain HTTP/2 flow control and END_STREAM behavior.

### T2 - Complete the HTTP/2 static path

**State:** completed locally - candidate retained

Reuse immutable HPACK metadata and response bodies, then reduce encrypted DATA
submission overhead. Disk consistency and the twenty-file workload contract
must remain intact.

### Q1 - Reduce HTTP/3 small-response work

**State:** active

Measure ACK-only packets, packets per response, encryption calls, stream-state
allocation, sends, and wakeups. Coalesce ACK and response data within the ACK
deadline, and reuse connection-local stream state without weakening recovery.

### Q2 - Complete the HTTP/3 static path

**State:** queued

Reuse immutable QPACK metadata and shared file bodies while retaining a
per-request disk consistency check. Validate PMTU, loss recovery, migration,
multipath, and interop after every retained change.

### G2 - Close the remaining HTTP/2 Gateway gap

**State:** queued

Reprofile only after H1, TLS, and static-path work lands. Keep a Gateway-only
change only when proxy and backend CPU measurements identify a remaining local
bottleneck.

### F1 - Final full-matrix gate

**State:** queued

Run every official cnetmod profile, compare the complete result with this
baseline, update the adapter revision, and submit the benchmark update only
after every regression is either fixed or rejected.
