# HTTP/1.1 与 WebSocket 踩坑记录

## HTTP/1.1

### 去掉发送子协程也需要验证整个连接路径

2026-11-09 的直接 io_uring send awaitable 通过部分写入等四组测试和官方 1047 个分片
位置，但三组 A/B 为 +0.55%、-2.91%、+107.62%。最后一组受到明显扰动，候选未保留。
减少源码中的子 task 不等于已经测得分配次数或端到端收益。

同日又在独立网络命名空间复测非阻塞即时发送，三组吞吐分别下降 15.63%、18.51%、
11.33%。正确性通过后仍恢复了原提交路径。两项实验都保持电源设置不动。

### 不要用共享 prepared response 缓存热点整数

方案：启动时准备 0 到 2047 的完整响应，baseline 路由直接复用。

结果：4 worker 提升约 2.2%，8 worker 下降约 4.3%，CPU/请求增加约 4%。16 worker 的方向也不稳定。

原因：官方请求集中返回少数整数。多个 worker 会反复修改同一批 `shared_ptr` 引用计数，对同一缓存行产生竞争。节省序列化后，跨核原子操作成了更大的成本。

线程本地缓存也没有解决问题。它在 4 worker 下下降约 2.5%，说明响应对象复用本身的工作仍然超过这几个字节的序列化成本。

重新尝试条件：响应表示改为连接本地、无原子引用计数，并且能在进入通用响应构造前选中。

### 不要把解析器微基准提升直接当作服务器提升

方案一：只清理本次出现的扩展头，减少 parser reset 写入。

结果：解析微基准提升约 2.05%，端到端 persistent HTTP 却从 457.29K/s 降到 453.56K/s。

方案二：把查询参数求和从两次搜索改成单次扫描。

结果：4 worker 持平；8、16 worker 的绝对中位数小幅上升，但 16 worker 三个配对中有两个下降，配对中位数约 -1.3%。

原因：新增的状态维护和分支会进入每个请求。解析器局部少几次写入，不代表完整请求少了调度、系统调用或缓存缺失。

重新尝试条件：perf 能把解析器定位为端到端主要用户态热点，并且修改不增加公共分支。

### 不要绕过 io_uring 直接同步发送小响应

方案：先尝试同步 `sendmsg`，失败后再回到异步发送。

结果：中位数从 414.89K/s 降到 374.00K/s。

原因：多一次系统调用和失败分支破坏了原有的一次 SQE 提交路径。小响应不等于同步发送更便宜。

重新尝试条件：内核提供可验证的无提交发送能力，或者现有发送不再是一条 SQE。

### 不要为小请求长期占用 provided buffer

方案：解析阶段直接借用 io_uring 注册缓冲区，避免复制请求头。

结果：持有缓冲区直到 SEND 会降低吞吐；提前释放虽恢复到 405.55–406.76K/s，仍低于 408.53–415.52K/s 的基线范围。

原因：缓冲区归还延迟会降低 buffer ring 周转率。生命周期管理成本也超过小请求复制。

2026-11-04 又验证了一个更完整的借用 parser。4 worker 的吞吐中位数约提高 2.8%，但 P99 变差；16 worker 吞吐约下降 4.2%。这说明只把生命周期写完整，仍不能解决高并发下的 buffer ring 周转问题。

### 不要用非正式构建决定对象布局优化

方案：把请求行和请求头字段的偏移、长度从 64 位压缩为 32 位，使每个字段从 40 字节降到 20 字节。

结果：无 LTO 构建在 4 worker 下曾显示大幅提高；相同代码进入 Clang 23 Release + ThinLTO 后，4 worker 中位数约下降 2.3%，8 worker 约下降 1.7%，16 worker只提高约 0.7%。候选已撤回。

原因：字段布局改变会同时改变模块内联和热函数排布。无 LTO 的结果只能帮助找方向，不能决定保留。

重新尝试条件：正式 ThinLTO 的 4、8、16 worker 都不回退，并补充内存占用下降数据。

### 不要为同步精确路由增加第二套公开上下文

方案：新增借用请求视图，让同步精确路由绕过完整 `request_context`；后续又让它直接命中
精确路由索引。

结果：首轮 4/8/16 worker 的配对中位数约为 +3.5%、+3.7%、+0.8%，方向没有跨档稳定；
直接索引版本在 4 worker 下约 -3.4%。

原因：新增 route 字段、共享 handler 间接调用和传输层分支抵消了对象初始化的节省。
这套 API 还扩大了用户需要选择的路由模型，却没有带来稳定收益。

重新尝试条件：现有同步 handler 可以在不增加 route 字段和公开 API 的前提下裁掉同一批工作。

### 不要把连接本地路由缓存当成主要缺口

方案：每条 HTTP/1 连接缓存最近两个精确 method/path 匹配，覆盖官方 GET/POST 轮换。

结果：4 worker 三个配对约为 +0.28%、+0.01%、+6.23%；CPU/请求的中位数只改善约
0.44%。第三轮同时出现 145 ms P99，属于宿主调度离群值。

原因：当前精确路由索引已经很轻。再加两项比较和缓存维护，只能省下很小一段哈希工作。

重新尝试条件：正式服务器 profile 显示路由哈希进入主要热点，并且可以用无额外比较的
连接状态复用命中结果。

### 不要在请求行前面叠加常见方法捷径

方案：GET/POST + HTTP/1.1 直接解析，其他输入回退到完整 method/version 逻辑。

结果：4 worker 三个配对约为 -3.6%、-0.1%、-3.9%，CPU/请求同步变差。

原因：原有字符串比较经过 ThinLTO 后已经很短。新增的前置分支扩大了最热函数，指令布局
成本超过省下的比较。

重新尝试条件：用生成式状态机整体替换请求行和头部解析，而不是在现有解析器前叠加分支。

### 不要只靠缩小热对象字段判断收益

方案：把 18 个常用请求头索引从 64 位缩成 16 位，并把每个请求头记录的四个偏移量从
64 位缩成 32 位。16 KiB 请求头上限能够保证取值范围。

结果：组合后的 4 worker 三个配对约为 +0.3%、-3.3%、+1.9%，中位数只有约 +0.3%；
CPU/请求也没有稳定下降。候选已撤回。

原因：对象体积确实下降，但官方混合请求只有少量头字段。这部分写入并不是足以决定端到端
吞吐的成本，代码布局变化反而会放大本机噪声。

### 不要把嵌套 task 机械替换为直接 awaitable

方案：让 multishot recv 的 `async_next()` 返回直接 awaitable，删掉每次接收创建的一层
`task` 协程，同时保持调用表达式不变。

结果：4 worker 配对中位数约 +0.9%，没有通过门禁；8 worker 三个配对约为 -5.6%、
+0.8%、-6.9%。CPU/请求下降时，完成请求数也下降。

原因：直接 awaitable 改变了调用方协程帧大小和恢复布局。少一层协程不等于事件循环能完成
更多请求，必须把唤醒进度和吞吐一起验证。

### 复用 HTTPS 方法枚举也要通过各档位对照

2026-11-09，Q5 让 HTTPS 路由复用解析器中的方法枚举，保留字符串回退。
官方 JSON-TLS 脚本的 4/8/16 worker 配对中位吞吐约为 -25.89%、+1.72%、+8.79%。
所有功能对照通过，但首档回退，因此候选撤回。同二进制校准也有约 8% 配对差异，
这轮无法单独证明源码修改造成了全部差异。

### 分块发送先验证正文和报文边界

Q6 发现 `std::move(response.body())` 仍是借用视图。随后清空 response 正文会使视图
失效，并重新加入 `Content-Length: 0`。明文与 TLS 的两个网络用例先失败，再在改用
头部序列化入口后通过。发送次数对照以已修复的三次发送版本作为基线。

首个诊断服务漏配 TCP_NODELAY，吞吐约 11K req/s。这组未完成测量已经排除，
按官方 socket 选项修正并重建两个版本后才做正式对照。单块合并后的最终记录包含一次
8 worker 负向波动和一次 16 worker 基线异常，随后两档均独立复跑并确认正向中位数。
原始轮次、内存代价和 syscall 计数均见推进记录 Q6。

## WebSocket

### 接收池布局与查找缓存仍需端到端验证

2026-11-06 将 provided-buffer ring 改为连续存储，4 worker 的三组零错误配对吞吐
约为 -0.3%、-6.9%、+6.3%，中位数未通过门禁，已经撤回。

同日为接收服务 registry 增加线程本地弱引用缓存。官方 gcannon 的三个原始请求模板在
每连接十次请求、512 连接下，4/8 worker 配对中位数约为 -0.47% 和 +0.29%。候选已撤回。
这组结果不足以判定 registry 锁是当前短连接场景的主要瓶颈。

第一次 4096 连接的 wrk 对照出现连接错误，整组数据作废。以后必须保存完成响应数和
连接错误，才能用相同压力下的有效结果判断收益。

### 单帧专用捷径没有稳定收益

方案一：单个借用帧直接交给 gather writer，绕过临时 vector。

结果：4/8/16 worker 分别约 +0.5%、-1.6%、+0.3%。

方案二：为完整、未分片、带掩码的文本和二进制帧增加专用解析分支。

结果：分别约 +0.7%、-2.7%、接近 0%。

原因：额外判断进入所有帧；原有小 vector 和通用解析器并不是端到端主要成本。

重新尝试条件：同一分支可同时替代多步状态机，并且 8 worker perf 显示帧解析占比明显上升。

### 写入批量阈值不能只看长连接

方案：把 io_uring 低延迟写阈值从 2 个 SQE 提高到 4 个。

结果：普通 echo 在 4/8/16 worker 提升约 4.5%、3.1%、3.9%，CPU/请求同步下降；短连接 echo 在 8、16 worker 下降约 2.4% 和 2.0%。

后续方案按消息数量切换阈值，但独立复跑使 16 worker 普通 echo 下降约 3.4%。

原因：长连接受益于合并提交，短连接需要更快完成最后一次写和关闭。用消息数量判断生命周期不能稳定代表队列状态。

重新尝试条件：提交策略能读取当前 SQ 队列和连接关闭状态，而不是依赖固定消息计数。
