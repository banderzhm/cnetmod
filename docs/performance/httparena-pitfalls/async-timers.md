# Async 延迟路由踩坑记录

## 测试口径

HttpArena `async` 使用 32,000 条长连接持续请求 `/delay/10`。理论吞吐上限约为
连接数除以 10 毫秒，因此判断优化时必须同时看达成率，不能只看绝对 RPS。

旧实验只用了 1,024 连接。新的诊断按每个 worker 512 条连接重新施压，使单个
事件循环面对的定时器数量接近官方环境。

## 提高 CQE 单轮收割上限没有收益

把 `CNETMOD_IOURING_CQE_TICK_LIMIT` 从 256 调到 1024 后，4 worker、2,048
连接的三轮响应数中位数从 1,954,889 变为 1,954,696，约下降 0.01%。官方
差距不是因为事件循环每轮最多处理 256 个 CQE。

## 提交批量 64 不适合延迟路由

把 `CNETMOD_IOURING_SUBMIT_BATCH` 从 16 调到 64 后，相同负载的三轮中位数
从 1,958,176 变为 1,954,199，下降约 0.20%。延迟完成后需要尽快提交小响应，
WebSocket 使用过的批量参数不能直接套到 async。

## 减少 worker 会降低总吞吐

固定 16 个 CPU 和 8,192 条连接时，4、8、16 worker 的单轮吞吐约为
318K、607K、718K RPS。减少事件循环没有改善共享资源竞争，反而使每个循环
承担更多连接和超时完成。

按每个 worker 512 条连接扩展时，4、8、16 worker 的理论上限达成率约为
95.5%、92.6%、88.0%。剩余问题在高并发扩展或压测端调度，而不是单个 timer
的实现成本。

## 重新尝试条件

只有在获得官方 32,000 连接运行的 `perf`、每 worker CQ 深度以及压测生成器
调度延迟后，才继续修改 async 热路径。缺少这些数据时，不再重做 timer 聚合、
CQE 上限、提交批量或减少 worker 的方案。
