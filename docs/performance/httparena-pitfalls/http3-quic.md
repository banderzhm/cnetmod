# HTTP/3 与 QUIC 踩坑记录

## 请求对象和头部复用

### 不要为了复用容量搬动完整请求对象

方案：回收整个 HTTP/3 request，保留内部字符串容量。

结果：吞吐中位数下降约 0.75%，CPU/请求增加约 5.67%。

原因：移动、清理和重新连接完整对象比保留少量连接内头部存储更贵。

当前保留方案只复用 session 内的 `header_map` 容量。它提升约 1.32%，CPU/请求下降约 1.95%。

### 不要逐项回收匹配的头字段

方案：保留名称和值相同的字段，擦除其余字段后再插入。

结果：吞吐下降约 11.64%，CPU/请求增加约 9.27%。

原因：排序容器的查找、擦除和插入比重新填充短头字段更贵。

### 头名称索引会制造新的公共成本

方案：跨请求保留头名称，并维护 seen index 来处理删除和重复头。

结果：吞吐下降约 5.52%，CPU/请求增加约 4.04%。

原因：为了少复制几个短名称，每个头都增加了索引维护和重复检测。

## STREAM 表示和所有权

### 拆分 owned STREAM header 造成严重回退

方案：把 STREAM header 和 HTTP/3 payload 分开保存，避免移动 payload。

结果：吞吐下降约 16.68%，CPU/请求增加约 19.27%。

原因：新的表示增加了调度、分支和分段处理。原来的连续 owned frame 对小响应更合适。

### shared prepared response 不适合几字节正文

方案：完整 wire image 通过共享 QUIC storage 复用。

结果：4 worker 下降约 11.5%。

原因：共享 owner、pending range 和 scheduler 工作超过复制几字节正文的成本。

当前保留方案把 HEADERS 与 DATA 完整预编码，但复制到现有 owned inline send buffer。它在 4/8/16 worker 分别提升约 10.1%、4.8%、2.8%。

### 非持有静态响应头存在生命周期代价

方案：用借用视图替代每请求 `shared_ptr` 引用计数。

结果：8、16 worker 一度出现约 4% 提升，但配对方向不稳定，4 worker 下降约 13.6%。

结论：没有稳定收益前，不暴露更脆弱的生命周期契约。

## Worker 与亲和性

### 不要自动按探测到的 CPU 列表绑 worker

方案：框架自动设置 worker affinity。

结果：4 worker 下降约 11.35%，8 worker 下降约 1.45%，只有 16 worker 提升约 2.20%，CPU/请求还略有增加。

原因：WSL 暴露的是虚拟 SMT 拓扑，连续逻辑 CPU 不等于独立物理核心。统一亲和策略会让不同 worker 数落在不同的核心组合上。

结论：worker 数仍测试 4、8、16，但框架不自动猜测部署方拓扑。

## Gateway-H3 边缘实现

### 不要把 Caddy 的上限归到 cnetmod 后端

公布成绩中，cnetmod 的 64 连接 Gateway-H3 消耗 2997.5% CPU。其中 Caddy
占 2654%，cnetmod 后端只占 343%。256 连接时，两者分别占 2063% 和
251%。因此，只压缩后端热路径无法填平总吞吐差距。

榜单前四名全部使用 stock nginx HTTP/3。相同 Caddy 组中的
`vanilla-epoll` 与 cnetmod 很接近，这也说明榜单中间出现的吞吐断层来自
边缘实现，而不是后端语言。

同一台 32 线程机器使用相同 cnetmod 后端、请求集和 8/8/16 CPU 分配做了
三轮 A/B。64 连接最好值从 11,038 提高到 16,950 RPS，提升 53.56%；
256 连接从 7,077 提高到 15,934 RPS，提升 125.15%。所有响应均为 2xx。

当前保留方案使用 stock nginx 1.27，按容器 cpuset 设置 worker 数，并保留
HTTP/1.1 keep-alive 上游连接池。这个方案仍然属于官方要求的两服务 Gateway
拓扑，没有改变请求集或资源预算。

4/8/16 worker 曲线显示，减少代理核心没有带来更好的综合结果。16 worker 在
256 连接时达到 13.19K RPS 中位数，而 4 和 8 worker 分别只有 6.14K 和
6.98K。由于本机为混合核心，单轮波动较大，因此这组数据只用于否决缩小代理
配额，不用于推算官方成绩。官方的 32/32 CPU 分配保持不变。

### QUIC GSO 必须显式开启

nginx 的 `quic_gso` 默认关闭。开启后，内核可以用一次 UDP 提交发送多个 QUIC
分段，从而减少系统调用和逐包提交成本。

同一后端、同一请求集的配对结果如下：

| Worker | 连接数 | 关闭 GSO 中位数 | 开启 GSO 中位数 | 提升 |
|---:|---:|---:|---:|---:|
| 4 | 64 | 9,545 | 11,460 | 20.07% |
| 4 | 256 | 6,706 | 10,391 | 54.94% |
| 8 | 64 | 10,000 | 16,954 | 69.54% |
| 8 | 256 | 11,792 | 15,920 | 35.01% |
| 16 | 64 | 10,040 | 21,684 | 115.98% |
| 16 | 256 | 10,182 | 20,788 | 104.16% |

六档全部返回 2xx，并且没有出现吞吐回退。目标跟踪表只采用最小提升
20.07%，不把本机 16 worker 的翻倍结果直接外推到官方机器。

### 不要无条件放大每个 QUIC socket 的缓冲区

方案：在每个 `reuseport` socket 上显式设置 1 MiB 收发缓冲。

结果：4 worker 下，64 和 256 连接的中位数都只提高约 0.1%，没有通过
1% 保留门槛。每个 worker 还会增加独立的内核缓冲占用。

结论：撤销显式 `rcvbuf` 与 `sndbuf`。当前工作负载的主要提交成本已经由 GSO
解决，扩大队列没有带来可量化收益。

### 不要关闭小响应的代理缓冲

方案：设置 `proxy_buffering off`，让上游响应直接进入 QUIC 输出路径。

结果：4 worker、64 连接的三轮中位数只提高约 0.56%，没有通过 1% 门槛；
256 连接首轮下降约 0.61%。

结论：保留 nginx 默认缓冲。它能把小的上游读取合并后再交给 QUIC，而关闭
缓冲没有减少足够的复制成本。

## 静态文件

### 少一个发送协程没有触及主要成本

方案：缓存 content-length，并让静态响应直接进入 inline send。

结果：4、8 worker 均约 -0.7%；16 worker 的绝对中位数提高约 6.9%，但三个配对方向不一致。

原因：静态 H3 的主要成本仍在 QUIC 分片、加密、恢复和 UDP 提交，不在一个发送协程。

### 延后磁盘路径校验不能稳定提升

方案：命中缓存后再构造和校验 `filesystem::path`。

结果：4 worker 只提高约 0.6%；8 worker 下降约 1.7%；16 worker 吞吐上升但 CPU/请求增加约 4.5%。

原因：路径构造不是所有 worker 数下的主要成本，而且变化没有同时改善效率。

重新尝试条件：静态文件缓存拥有不可伪造的已校验文件标识，并且 perf 再次显示路径处理进入主要热点。

## ACK 解码

### 范围数组少复制，空范围仍需单独复核

2026-11-09，Q3 将普通 ACK 的两次范围数组复制改为移动，同时在分配前检查报文长度。
首版对空范围也做分配边界检查，局部基准从 8.02ns 增至 10.64ns，因此没有保留首版。

最终实现让空范围跳过分配准备。三组 AB/BA/AB 的中位数在 0、1、8、64 个附加范围下，
分别变化约 -2.49%、-9.77%、-0.12%、+1.21%。负值表示解码耗时减少。
其中 64 范围当轮稍慢，尚不能确认回退，也不能把其他范围的变化当作 HTTP/3 吞吐提升。

保留修改的依据是明确减少数组复制，并在分配前拒绝不可能的范围数量。175 项测试通过。
执行记录 Q3 保存了原始目录和测量条件，目标表没有据此增加预计成绩。

## 原文头字段

### 分开测编码与解码，并让接收端读取完整内容

2026-11-09，Q4 同时尝试 QPACK 原文解码和字段名编码的批量复制。第一轮中，
长值编码变慢约 7%–12%，所以缩小为三处解码修改，另保留 HPACK 原文编码修改。

随后让解码 sink 对字段名和值的全部字节做哈希。QPACK 原文解码的局部耗时仍减少
71%–95%，180 对样本的内容校验一致。不过，源码未改的 QPACK 编码控制项仍在
-12.74% 到 +19.37% 之间变化，因此前一次编码慢点也不能直接归因为批量复制。

结论是保留较小的解码修改，并记录编码候选的测量限制。源码中的逐字节循环值得检查，
但重新尝试编码前，应先确认控制项足够稳定。局部字段收益也需要与 HTTP 吞吐分开记录。
