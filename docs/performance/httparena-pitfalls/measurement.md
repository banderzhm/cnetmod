# 压测与判断方法踩坑记录

## 先用同一二进制校准噪声

2026-11-09 的 A/A 校准发现，4/8/16 worker 的最大配对差异分别达到
6.88%/10.31%/30.01%。因此当前宿主负载下，1% 门槛不足以判断候选收益。
先让 A/A 重复性达到所需精度，再运行交错 A/B 和独立复跑。三组配对只能说明本轮
观察到的波动范围，不能直接当成统计置信界限。

WSL 镜像网络还会将 `127.0.0.1` 经 `loopback0` 发往 Hyper-V。只换目的地址成
`127.0.0.2` 仍可能以 `.1` 为源地址，导致回包继续绕行。必须检查双向路由与实际连接
地址。同一二进制在双向 Linux 回环下的吞吐明显升高，但仍有较大波动。
临时路由在测试结束后已删除。完整日志和 profile 位置见执行记录的 M1 条目。

M2 又验证了持续服务进程、较少压测线程、隔离网络命名空间、关闭睿频、20 秒预热和
单 SMT 压测掩码。这些对照仍未通过 1% 精度门禁。具体原因尚未隔离，不能把大幅 A/A
差异统一归因于某一个因素，也不能只保留其中接近零的一组。Windows 电源设置和临时路由
已恢复。此前小幅收益与小幅回退均按本地证据不足处理，历史排名外推暂停使用。

## 检查 perf 的 ELF 与展开支持

2026-11-09 的 perf 可采集 cpu-clock，但编译时关闭了 libelf 和 DWARF 展开。
用户态采样因此散落在十六进制地址上。换用本机缓存包中的完整工具后，已有采样成功
还原到函数。采集程序能运行，并不足以证明函数热点报告已经可用。

`http1_calibration.sh` 现在先检查这两项能力，并将构建选项存档。
可用 `PERF_BINARY` 显式选择完整工具。缺少能力时，脚本在启动服务前结束。
相关原始报告、工具版本与校验见推进记录 Q5。

## 不看单轮最好值

本机是大小核处理器，WSL 又暴露虚拟 SMT 拓扑。持续压测后，后置运行的一方曾比前置运行的一方低约 15%。这不是足够可靠的候选差异。

正确做法：

- 基线与候选交错运行；
- 使用 ABBA 或平衡顺序；
- 轮次之间留出冷却时间；
- 保存每一轮，不只保存最好值；
- 同时看绝对中位数和配对变化。

## 4、8、16 worker 都是门禁

多个候选只在一个 worker 数下有效：

- 自动亲和性只改善 16 worker，却严重损伤 4 worker；
- prepared integer cache 改善 4 worker，却损伤 8 worker；
- 单数字正文捷径改善 16 worker，却损伤 4、8 worker；
- WebSocket 写阈值改善长连接，却损伤短连接。

因此本机验证固定覆盖 4、8、16 worker。一个档位的提升不能抵消另一个档位超过 1% 的稳定回退。

## 微基准只负责定位

解析器微基准曾提升约 2.05%，端到端却下降。微基准可以说明某段代码更快，但不能说明服务器更快。

保留条件必须来自官方形状的端到端压测。微基准只用于解释变化来源。

## CPU/请求与吞吐必须同方向

如果吞吐上升而 CPU/请求增加，需要先排除：

- load generator 饱和；
- 主机频率变化；
- 队列积压；
- 把工作转移到代理或内核；
- 失败请求被计入吞吐。

候选至少应做到吞吐稳定提升且 CPU/请求不恶化。固定速率项目还要检查 rate ratio、mean、p99 和 p99.9。

## 关联项目决定能否保留

同一处底层修改必须运行关联门禁：

| 修改位置 | 必跑项目 |
|---|---|
| HTTP/1 解析与写入 | baseline、limited-conn、pipelined、Gateway backend |
| HTTP/2 HPACK 与响应队列 | baseline-h2、baseline-h2c、json-h2c、static-h2、gRPC |
| WebSocket 接收与提交 | echo-ws、echo-ws-pipeline、echo-ws-limited |
| QUIC STREAM 与 UDP | baseline-h3、static-h3、Gateway-H3、QUIC/HTTP3 测试组 |
| 压缩 | json-comp、json-tls、static-tls、Gateway |

最典型的反例是 WebSocket 阈值四：普通 echo 提升 3%–5%，短连接却下降约 2%。如果只跑目标项目，这个改动会被错误保留。

## 压缩项目要计算得分公式

json-comp 不按原始 RPS 单独排名。gzip level 1 的吞吐更高，但正文更大，加权得分反而下降约 25%。

每次压缩实验必须保存：

- Content-Encoding；
- 每个官方请求形状的压缩字节数；
- 平均带宽；
- 原始 RPS；
- 按官方公式计算的有效 RPS。

## 结束实验时清理现场

被淘汰的候选必须同时清理：

- 源码和公开 API；
- 临时测试；
- benchmark 脚本；
- 生成的中间结果；
- 只为候选增加的配置项。

最后运行 `git diff --check`，并确认工作区只剩已经通过门禁的改动。
